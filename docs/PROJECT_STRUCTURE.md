# Project Structure

The full repo tree, directory by directory — what's here, what owns it,
and what it's for. `lib/`'s *internal* structure (feature modules, the
`data`/`presentation` split) has its own deeper treatment in
[Flutter.md](Flutter.md#structure); this file is the outside-in map of
everything else.

## Top level

```
yovoice/
├── lib/                    Flutter app source — see Flutter.md
├── functions/               Cloud Functions (Node) — see Backend.md
├── firestore-tests/          Firestore rules test suite — see TESTING.md
├── test/                    Dart unit/widget tests — see TESTING.md
├── docs/                    Project documentation (this tree)
├── assets/                  Fonts, icons, images, animations bundled into the app
├── android/ ios/ web/       Per-platform Flutter build scaffolding —
│  macos/ windows/ linux/    generated by `flutter create`, then customized
│                            per platform (signing config, entitlements,
│                            launch screens, app icons)
├── .github/workflows/        CI — see DEPLOYMENT.md
├── firebase.json             Firebase project config (Hosting, Firestore,
│                            Storage, Functions source) — see Firebase.md
├── .firebaserc                Which Firebase project `firebase` CLI
│                            commands target (`yovoice-ec54a`)
├── firestore.rules            Firestore Security Rules — the
│                            authorization layer, see SECURITY.md
├── firestore.indexes.json      Firestore composite indexes + field
│                            overrides
├── storage.rules              Cloud Storage Security Rules
├── pubspec.yaml / .lock        Flutter/Dart dependencies — see
│                            DEPENDENCIES.md
├── analysis_options.yaml       `flutter analyze` lint configuration
├── CLAUDE.md                  Working conventions for this repo
├── README.md                  Entry point / landing page
└── .yovoice_backups/           Dated pre-change snapshots from early
                              development — see "Legacy artifacts" below
```

## `lib/` — the Flutter app

Feature-based: `lib/features/<feature>/{data,presentation}/`, plus
cross-cutting `lib/core/` (theme, helpers) and `lib/shared/` (reusable
widgets). Full breakdown, including *why* feature-based over layer-based,
in [Flutter.md](Flutter.md) and
[ADR-015](Decisions.md#adr-015-feature-based-folder-structure-over-layer-based).

## `firestore-tests/` — Firestore rules test suite

A standalone Node project (its own `package.json`, `node_modules/`) that
runs regression and attack-scenario checks against `firestore.rules` and
`storage.rules` via the Firestore and Storage emulators — three suites,
301 + 46 + 11 checks as of 2026-08-16. Not part of the Flutter app's
dependency tree at all — see [TESTING.md](TESTING.md) and
[`firestore-tests/README.md`](../firestore-tests/README.md) for the actual
workflow.

## `test/` — Dart tests

Standard Flutter test location (`flutter test` looks here by default).
**52** `*_test.dart` files carrying 438 tests as of 2026-08-16 (counted
with `find test -name '*_test.dart'`; the test total is from the suite
run). Coverage is regression-driven and uneven, not uniform — see
[TESTING.md](TESTING.md) for what is actually covered and what is not.

## Platform folders (`android/`, `ios/`, `web/`, `macos/`, `windows/`, `linux/`)

Standard Flutter platform scaffolding, mostly generated and then
hand-customized: signing configuration, entitlements, app icons, launch
screens, and (on `macos`/`windows`) the generated plugin registrant files
that change automatically whenever a native-plugin dependency is added or
removed — don't hand-edit those, they're regenerated by `flutter pub get`.
`ios/Runner/Assets.xcassets/LaunchImage.imageset/README.md` is Xcode's own
boilerplate explaining that folder — unrelated to this documentation
system, left as Xcode generated it.

## Legacy artifacts (tracked, not actively maintained)

A few root-level files are holdovers from earlier, faster-moving
development and predate the current documentation/workflow conventions.
They're git-tracked (not gitignored) but aren't part of any current
workflow:

- **`install_room_types.py`, `patch_room_screen.py`** — one-time Python
  scripts that copied/patched specific `lib/` files during the rooms
  rebuild (see [Archive/ROOMS_REBUILD_PLAN.md](Archive/ROOMS_REBUILD_PLAN.md)).
  Not part of any current build or deploy step.
- **`yovoice_vscode_cleanup.sh`** — a one-time VS Code workspace-settings
  setup script.
- **`.yovoice_backups/`** — dated snapshot folders (e.g.
  `fix_host_controls_overflow_20260725_013447/`) taken as manual,
  pre-change safety nets during a period of rapid iteration — the informal
  predecessor to the git-tag-based backup habit described in
  [ADR-002](Decisions.md#adr-002-git-workflow-push-straight-to-main-no-prs).
  Real git history has fully superseded the need for this pattern; these
  are kept as-is rather than deleted, consistent with this project's
  general bias toward archiving over deleting.

None of these need to be run, read, or maintained for normal development
— they're mentioned here so nobody mistakes them for part of the current
workflow, and so "what is this file" has an answer if someone goes
looking. If they're ever cleaned up, that's a housekeeping change, not a
documentation one — this file will be updated to match whenever that
happens.

## What's intentionally not tracked in git

`build/`, `.dart_tool/`, `.flutter-plugins-dependencies`, `*.log`
(including the Firestore emulator's `firestore-debug.log`), `.idea/`,
`.vscode/` settings, and standard platform build artifacts — see
`.gitignore` for the authoritative list. `node_modules/` under both
`functions/` and `firestore-tests/` is similarly untracked and regenerated
via `npm install`.
